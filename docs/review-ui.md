# 레시피 리뷰 화면 설계

- 상태: 초안 · 2026-10-26 — 구현 전. **구현은 마지막 단계(M9)** 다.
- 서비스 전체 구조는 [design.md](design.md), 레시피 형식은 [recipe-spec.md](recipe-spec.md). 이 문서는 레시피 변경을 **사람이 보고 반영하는 웹 화면**이다.
- 제안·반영 조건·반영·되돌리기의 **규칙과 MCP 도구는 design §6.4~6.5 가 정본**이고 M6 에서 먼저 구현된다. 이 화면은 같은 함수를 부르는 또 하나의 입구다. 화면이 생기기 전에는 `recipe_proposal`·`recipe_diff` 가 리뷰 수단이다.

---

## 1. 무엇을 하나

레시피는 빌드 머신 안 git 저장소에 있고 외부 원격이 없다(design §6.4). 의미 차이와 반영 조건은 MCP 결과로도 읽을 수 있지만, 여러 프로젝트에 걸친 변경을 사람이 훑어보기에는 화면이 낫다.

| 한다 | 하지 않는다 — 이유 |
|---|---|
| 제안 목록과 상세 | **레시피 편집** — 편집은 Claude 의 `recipe_edit` 로만 한다. 저장 전 검사·충돌 처리를 두 곳에서 하지 않는다 |
| **의미 차이**(단계·툴체인·파라미터·권한이 어떻게 바뀌나)와 파일 차이 | **빌드 시작** — 시도 실행은 MCP 로 건다. 화면은 그 결과를 보여 준다 |
| 반영 조건과 그 상태 | 줄 댓글·좌우 보기·구문 강조 — 1단계 규모에 비해 비용이 크다(§15) |
| 제안 단위 댓글 — Claude 가 MCP 로 읽고 반영할 수 있다 | 외부 공개 — tailnet 안에서만, 로그인한 팀원만 |
| 반영·닫기·되돌리기(권한별) | 알림(메신저 등) — 1단계 밖(§15) |
| 레시피 탐색(파일, 겹친 결과), 이력, 작업 상세 보기(읽기) | |

## 2. 개념 — 제안(proposal)

**제안 = `recipe/*` 브랜치 하나 + 제목·설명·상태**, 고유 id(`p0012`). 생애는 design §6.5:

- 새 `recipe/*` 브랜치에 첫 `recipe_edit` 이 일어나면 열린다(제목 = 첫 커밋 메시지, `recipe_propose` 로 고친다).
- 반영되면 브랜치 ref 를 지운다(커밋은 `main` 이력에). 닫으면 커밋을 `refs/cimon/closed/<id>` 로 옮긴다. 같은 브랜치 이름은 다시 쓸 수 있고, 다시 쓰면 새 제안이 열린다 — 그래서 화면 주소는 브랜치 이름이 아니라 **제안 id** 다.
- 30일 동안 커밋도 시도 실행도 없으면 자동으로 닫힌다.

## 3. 화면 목록

모든 경로는 `https://cimon.<tailnet>.ts.net/ui/…` 아래다.

| 경로 | 화면 | 주 사용자 |
|---|---|---|
| `/ui/` | 첫 화면 — 열린 제안, 최근 반영, 최근 작업, 백업 상태 | 모두 |
| `/ui/proposals` | 제안 목록(열림·반영됨·닫힘 필터) | 모두 |

| `/ui/recipes/<ref>/tree/<path>` | 파일 보기(브랜치·커밋 기준) | 모두 |

## 4. 제안 상세 화면

### 4.1 생김새

```
+--------------------------------------------------------------------------------------+
| cimon > 제안 > p0012  recipe/add-desktop-test                        admin-a (관리자) |
+--------------------------------------------------------------------------------------+
| desktopTest 단계 추가                                                     [open]      |
| 작성 member-b · 3시간 전 · head 7c1e9a2 · 기준 main a1b2c3d                          |
|                                                                                      |
| 반영 조건                                                                            |
|   [통과] 정적 검사 — head 7c1e9a2                                                     |
|   [통과] main 에 fast-forward 가능                                                    |
|   [통과] 시도 실행 — example-app: j000214 pass                                        |
|          (head 7c1e9a2, 바뀐 단계 test-shared-desktop 포함)                           |
|   [ - ]  시험할 수 없는 변경 — 없음                                                   |
|                                                     [ 반영 ]  [ 닫기 ]               |
+--------------------------------------------------------------------------------------+
| [의미 차이]  [파일 차이 (1)]  [시도 실행 (2)]  [댓글 (3)]                              |
+--------------------------------------------------------------------------------------+
| 영향받는 프로젝트: example-app                                                        |
|                                                                                      |
| example-app                                                                          |
|   단계 추가  test-shared-desktop  (test, 기본 아님)                    [실행]          |
|     run   ./gradlew.bat :shared:desktopTest --console=plain                           |
|     cwd   app                                                                         |
|     judge junit  reports=app/shared/build/test-results/desktopTest/*.xml              |
|           min_tests=1                                                                |
+--------------------------------------------------------------------------------------+
```

### 4.2 머리

- 제목·상태·작성자·**head 커밋**(지금 보고 있는 내용)·**기준 커밋**(갈라져 나온 `main`).
- head 가 바뀌면(누가 그 사이 `recipe_edit`·`recipe_sync`) 화면 위에 「이 제안은 7c1e9a2 → 9f3b2e4 로 바뀌었다 — 새로 고침」 띠를 띄우고 반영 버튼을 막는다(§4.7).

### 4.3 반영 조건

조건과 판정 규칙은 design §6.5 의 표 그대로다 — 정적 검사, fast-forward, 시도 실행(바뀐 단계를 포함한 head 의 최신 실행), 시험할 수 없는 변경. 화면은 `cimon-recipestore` 의 같은 함수 결과를 보여 준다.

- 각 조건은 **통과 · 실패 · 계산 중 · 계산 실패 · 해당 없음** 중 하나다. 「계산 실패」 는 통과로 보이지 않는다(§13).
- fast-forward 가 안 되면 해결 방법을 같이 보여 준다: 「Claude 에게 『recipe/add-desktop-test 를 main 에 맞춰 줘』 라고 요청 — `recipe_sync` 가 병합 커밋을 만들고, 충돌이면 세 내용을 보고 해결한다. 새 head 이므로 시도 실행을 다시 돌려야 한다」.
- 시도 실행 조건이 안 채워졌으면 프로젝트별로 이유와 필요한 호출을 보여 준다: 「example-app: head 7c1e9a2 로 돈 작업 중 바뀐 단계 test-shared-desktop 을 포함한 것이 없다 — `test(project="example-app", recipe_ref="recipe/add-desktop-test", steps=["test-shared-desktop"])`」.
- 시험할 수 없는 변경(`project.toml`, 카탈로그 설치 항목)이 있으면 그 목록과 「관리자가 `cimon provision --recipe-ref` 로 설치해 시도 실행에 쓰면 시험된 것으로 친다. 아니면 사유를 적고 반영」.

### 4.4 의미 차이

**파일 차이만으로는 「무엇이 실행되게 바뀌나」 를 읽기 어렵다.** 프리셋·include·카탈로그를 겹친 결과를 `main` 과 head 에서 각각 만들어 비교한다(`cimon-recipe` 의 겹치기 그대로). 반영 조건의 「영향받는 프로젝트」·「바뀐 단계」 도 이 결과에서 나온다.

1. **영향받는 프로젝트를 정한다**: 바뀐 파일이 `projects/<id>/` 아래면 그 프로젝트. 프리셋·카탈로그·공용 스크립트가 바뀌면 그것을 쓰는 모든 프로젝트.
2. 프로젝트마다 겹친 레시피를 비교한다.
   - 단계: id 기준으로 추가·삭제·변경, 변경이면 필드별(`run`·`cwd`·`env`·`judge`·`after`·`default`·`needs`·`timeout_min`·`uncounted`·산출물 …). 그 단계가 쓰는 스크립트 파일이 바뀌어도 「변경」 이다
   - 툴체인 요구, 파라미터, fixture, 작업 공간(`keep`·`clean_env`), `[env]`·`[isolate]`·`[account_env]`
   - `project.toml`
3. 카탈로그 차이: 종류 추가·삭제, 설치 방식·URL·체크섬 출처·스크립트 변경(항목 해시가 바뀐 종류).
4. 스크립트 파일 차이: 어떤 단계가 그 스크립트를 쓰는지 함께.

**위험 표시** — 리뷰어가 먼저 볼 것을 표시한다.

| 표시 | 언제 | 왜 |
|---|---|---|
| **[권한]** | `project.toml` 의 `repo`·`allowed_refs`·`[[sibling]]` 변경, 새 프로젝트 | 반영되면 빌드할 수 있는 저장소·브랜치가 바뀐다(design 원칙 7) |
| **[실행]** | `run`·`shell`·`cwd`·`env`·`account_env`, 판정·검사 스크립트의 명령과 **파일 내용**, fixture 명령의 추가·변경 | 빌드 머신에서 실행되는 명령이 바뀐다 |
| **[공급망]** | 카탈로그의 URL·체크섬 출처·설치 방식·설치 스크립트 커밋 변경, 새 종류 | 받아 오는 바이너리가 바뀐다 |
| **[동작]** | `default`·`needs`·`tags`·`timeout_min`·`fail_on_output`·판정 기준 변경 | 무엇이 돌고 무엇을 통과로 칠지가 바뀐다 — 판정을 느슨하게 하는 변경(`min_tests` 감소, `fail_on_output` 삭제, `uncounted` 추가, `cargo-test`·`junit` → `exit`, `on_up_failure` `code` → `infra`)은 **[동작·완화]** 로 따로 |

의미 차이를 계산하지 못하면(겹치기 실패 등) 빈 화면이 아니라 「의미 차이 계산 실패: <오류> — 파일 차이를 보라」 를 띄운다.

### 4.5 파일 차이

- 파일별 unified diff, 줄 번호. 구문 강조·좌우 보기는 하지 않는다.
- 파일 목록에 위험 표시를 같이 붙인다.

### 4.6 시도 실행 · 댓글

**시도 실행 탭**: 이 제안의 브랜치로 돈 작업 목록 — 작업 번호, 프로젝트, 도구·돈 단계, 판정·실패 분류, **어느 head 로 돌았나**, 반영 조건에 쓰였나. 현재 head 가 아닌 것은 흐리게 「이전 커밋」. 작업 번호는 `/ui/jobs/<job>` 로 이어진다.

**댓글 탭**: 제안 단위 댓글. 댓글에는 그때의 head 커밋이 기록돼, 이후 head 가 바뀌면 「이전 커밋에 단 댓글」 로 보인다.

- Claude 는 `recipe_proposal` 로 댓글을 읽는다 — 「리뷰 댓글 반영해 줘」 → 읽고 `recipe_edit` → 새 head → 반영 조건 다시 계산.
- 댓글은 Markdown 을 **글자 그대로**(굵게·코드 정도만) 보여 준다. HTML 은 쓰지 못한다(§10.3).

### 4.7 반영 · 닫기

- **반영**(관리자): 버튼은 화면이 보여 준 **head 커밋을 함께 보낸다.** 서버는 `recipe_promote` 와 같은 함수로 반영 순간에 조건을 **다시 계산**하고(화면의 상태를 믿지 않는다), head 가 다르면 「제안이 그 사이 바뀌었다 — 다시 보라」 로 거절한다. **fast-forward 만** 한다 — 병합 커밋을 반영 때 만들지 않는다.
- **조건을 덮어쓰는 반영**: 시도 실행 조건이 안 채워졌거나 시험할 수 없는 변경이 있을 때 관리자는 **사유를 적어야** 반영할 수 있다. 사유는 제안·이력·감사 로그에 남고, 이력 화면에 「조건 덮어씀」 표시가 붙는다. 정적 검사·fast-forward 는 덮어쓸 수 없다.
- **닫기**(작성자·관리자): 사유 선택 입력.

---

## 5. 이력 · 되돌리기

- `main` 의 커밋 목록: 작성자·시각·메시지·**어느 제안으로 들어왔나**·조건 덮어씀·되돌리기 여부.
- 커밋을 누르면 그 커밋의 의미 차이·파일 차이.
- **되돌리기**(관리자): 되돌리는 커밋을 미리 보여 주고(의미 차이), **사유를 적고** 확인하면 `recipe_revert` 와 같은 동작. 되돌린 결과도 정적 검사를 통과해야 한다.

## 6. 레시피 탐색

- **파일 보기**: 브랜치·커밋 선택, 디렉터리 트리, 파일 내용(줄 번호), 그 파일의 이력.
- **겹친 레시피**: 프로젝트 하나의 단계 표(id·종류·태그·기본·needs·after·판정·산출물), 툴체인, 파라미터, fixture. 각 항목이 어느 파일(프리셋·include)에서 왔는지 표시.

---

## 7. 작업 상세(읽기)

`job_status` 의 웹판. 판정·실패 분류·요약·경고, 커밋·레시피 커밋·시도 여부, 제외된 단계, 단계별 결과·시간·판정 지표, 단계 로그 끝 200줄(ANSI 제어 문자 제거), 산출물 목록과 다운로드 링크(새로 발급), `provenance.json`. 화면이 켜져 있으면(`[web].enabled`) MCP 결과에 이 화면의 주소(`job_url`)를 싣는다.

## 8. 로그인과 권한

### 8.1 일회용 링크로 로그인

브라우저에 Bearer 토큰을 넣게 하지 않는다. 대신:

1. Claude 에게 「리뷰 화면 열어 줘」 → MCP `web_login` 이 **5분짜리 일회용 링크**를 돌려준다(`https://cimon.<tailnet>.ts.net/ui/login?code=…`). 링크는 그 토큰의 사용자에 묶인다.
2. 링크를 열면 세션 쿠키가 생기고 코드는 바로 소모된다.
3. 제안·작업 링크를 로그인 없이 열면 「Claude 에게 리뷰 화면 로그인 링크를 요청하라」 와 토큰 입력 칸(대체 경로)을 보여 준다.

화면이 켜져 있으면 `recipe_edit`·`recipe_propose`·`recipe_proposal` 결과에도 제안 화면 주소를 싣는다.

Tailscale 신원 헤더는 여기서도 **인증에 쓰지 않는다** — 빌드 머신의 로컬 프로세스가 `127.0.0.1` 로 직접 들어오며 헤더를 꾸밀 수 있다(design §15.2).

### 8.2 세션

| 항목 | 값 |
|---|---|
| 쿠키 | `HttpOnly` · `Secure` · `SameSite=Strict` · 경로 `/ui` |
| 수명 | 12시간(`[web].session_hours`), 로그인할 때마다 새 세션 id |
| 저장 | 세션 id 의 해시만 DB 에 |
| 끊기 | 토큰을 끄면(`users.disabled_at`) 그 사용자의 세션도 끊긴다 |

### 8.3 권한

MCP 도구와 같다(design §6.4).

| 동작 | 팀원 | 관리자 |
|---|---|---|
| 모든 화면 보기 | ● | ● |
| 댓글 | ● | ● |
| 자기 제안 닫기 | ● | ● |
| 남의 제안 닫기 | | ● |
| 반영(조건 충족) | | ● |
| 반영(조건 덮어쓰기, 사유 필수) | | ● |
| 되돌리기(사유 필수) | | ● |

## 9. MCP 도구

제안·반영 도구(`recipe_proposals`·`recipe_proposal`·`recipe_propose`·`recipe_comment`·`recipe_close`·`recipe_sync`·`recipe_promote`·`recipe_revert`)는 design §6.4 에 있고 M6 에서 구현된다. 이 화면이 더하는 도구는 하나다.

## 10. 구현

### 10.1 구성

| 부분 | 선택 | 이유 |
|---|---|---|
| 서버 | 같은 `cimon.exe`, 같은 `127.0.0.1:8770` 의 `/ui/*` 경로(axum) | 배포 단위를 늘리지 않는다. `tailscale serve` 가 그대로 내보낸다 |
| 화면 | **서버 렌더링 HTML**(maud — 기본이 이스케이프), 상호작용은 작은 JS(htmx 수준, 실행 파일에 포함) | 프런트 빌드 파이프라인을 따로 두지 않는다. JS 가 꺼져도 폼 POST 로 동작 |
| 정적 자원 | 실행 파일에 포함(rust-embed). **외부 CDN 없음** | tailnet 안에서만 돈다. 외부 의존 없이 |
| 차이 계산 | `similar` 크레이트(파일 차이), `cimon-recipestore` 의 의미 차이·반영 조건 함수 | 화면과 MCP 가 같은 함수를 부른다 |
| 테마 | CSS 변수로 밝은·어두운(`prefers-color-scheme`) | |

코드는 크레이트 `cimon-web` 에 둔다(라우트·템플릿·자원).

### 10.2 반영 조건 계산

- 저장하지 않는다. `(head, main, 그 head 의 시도 작업 목록)` 을 키로 메모리에 캐시하고, 키가 바뀌면 다시 계산한다. 반영 순간에는 캐시를 쓰지 않고 새로 계산한다(design §6.5).
- 계산 중이면 화면은 「계산 중」, 실패하면 「계산 실패 + 오류」.

### 10.3 보안

| 위협 | 대응 |
|---|---|
| XSS — 레시피 파일·스크립트·댓글·로그는 모두 사용자 입력이다 | 템플릿 기본 이스케이프, 댓글 Markdown 은 허용 목록(굵게·기울임·코드·링크 텍스트)만, **CSP** `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; frame-ancestors 'none'; base-uri 'none'`, 인라인 스크립트 없음 |
| CSRF | `SameSite=Strict` + 폼마다 세션별 CSRF 토큰. 상태를 바꾸는 것은 POST 만 |
| 클릭재킹 | `frame-ancestors 'none'` |
| 로그인 코드 탈취 | 5분, 일회용, 사용자에 묶임, 해시만 저장. 로그인 시도 빈도 제한 |
| 리뷰어가 본 것과 다른 것이 반영됨 | 반영 요청에 head 커밋, 서버가 재계산(§4.7) |
| 권한 우회 | 모든 동작을 서버에서 역할로 검사 — 화면에서 버튼을 숨기는 것은 편의일 뿐 |

## 11. 데이터 모델 추가

제안·댓글 테이블(`proposals`·`proposal_comments`)은 design §13 에 있다. 화면 전용은 둘이다.

```sql
CREATE TABLE web_sessions (
  id_sha256    TEXT PRIMARY KEY,
  user         TEXT NOT NULL,
  csrf         TEXT NOT NULL,
  created_at   TEXT NOT NULL,
  expires_at   TEXT NOT NULL,
  last_seen_at TEXT,
  revoked_at   TEXT
);

CREATE TABLE login_codes (
  code_sha256 TEXT PRIMARY KEY,
  user        TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  expires_at  TEXT NOT NULL,
  used_at     TEXT
);
```

`audit.action` 에 `web_login` 을 더한다. 만료된 세션·로그인 코드는 하루 뒤 정리한다(design §16.4).

## 13. 화면에서도 실패는 실패로 보인다

| 상황 | 화면 |
|---|---|
| 반영 조건 계산이 실패했다 | 「계산 실패」(빨강) + 오류. 통과로 보이지 않는다. 반영 버튼 막힘 |
| head 가 화면을 연 뒤 바뀌었다 | 위쪽 띠 + 반영 버튼 막힘. 서버도 거절(§4.7) |
| `main` 이 움직여 fast-forward 가 안 된다 | 「fast-forward 불가 — `recipe_sync` 필요」, 반영 버튼 막힘 |
| 의미 차이를 만들지 못했다 | 「의미 차이 계산 실패」 — 빈 차이로 보이지 않는다 |
| 바뀐 것이 없다 | 「변경 없음」, 반영 버튼 막힘 |
| 시도 실행이 `inconclusive` | 통과로 치지 않는다(`trial_must_pass`). 실패 분류를 함께 |
| 시도 실행이 바뀐 단계를 안 돌렸다 | 「바뀐 단계 X 를 포함한 실행 없음」 — 다른 단계가 통과한 실행으로 채워지지 않는다 |
| 판정을 느슨하게 하는 변경 | **[동작·완화]** 표시를 맨 위에 |
| 조건을 덮어쓴 반영·되돌리기 | 제안·이력에 사유와 함께 영구 표시 |
| 외부 백업이 낡았다 | 첫 화면과 제안 상세 위에 경고 띠(design §16.5) |

## 14. 완료 기준 — M9

설계 문서의 다른 단계처럼 실패 경로를 포함한다.

- 제안 상세에서 의미 차이·파일 차이·반영 조건·시도 실행·댓글이 보인다. 프리셋을 고친 제안은 그 프리셋을 쓰는 모든 프로젝트를 「영향받는 프로젝트」 로 보인다.
- 화면을 연 뒤 Claude 가 같은 브랜치를 고치면, 반영 버튼이 막히고 서버도 반영을 거절한다.
- 팀원이 반영을 시도하면 403 과 이유. 관리자가 조건 미충족으로 반영하려면 사유를 요구한다.
- 화면의 반영 조건이 같은 제안에 대한 `recipe_proposal` 결과와 같다.
- `run` 을 바꾼 제안에 [실행], `min_tests` 를 낮춘 제안에 [동작·완화] 가 붙는다.
- 레시피 파일·댓글에 `<script>` 를 넣어도 글자 그대로 보인다(CSP 위반 보고 0건).
- 일회용 로그인 링크는 두 번째 사용과 5분 뒤 사용이 실패한다.
